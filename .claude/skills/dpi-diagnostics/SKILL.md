# Диагностика DPI и подбор стратегий

Опирается на `docs/manual.en.md` zapret2 (главы «blockcheck2», «Why it won't
open») и `blockcheck2.d/standard/*.sh`. Ключи движка описаны в skill
`nfqws2-engine`, функции — в `nfqws2-lua`.

## 0. Главные правила

1. **Подбираем только на заблокированном.** Если ресурс открывается без
   обхода (baseline OK), любая стратегия даёт «OK», и это не информация.
   Baseline меряется **всегда, до и после** перебора: блокировка может
   меняться во времени.
2. **Успех = полная загрузка, а не handshake.** HEAD или первые байты не
   доказывают ничего: блок «16 KB» рвёт соединение после ~16–20 KB входящих.
   Критерии успеха в §3.
3. **Повторяемость.** DPI часто стоит за балансировщиком. Стратегия
   признаётся рабочей при ≥ N/N успехов (по умолчанию 3/3 на этапе поиска и
   5/5 на финальной проверке), паузы между попытками 0,5–2 с.
4. **Не долбить.** Один хост в один момент тестирует один поток. Между
   прогонами к одному IP соблюдается rate-limit. Признаки «наказания» (§2.9)
   останавливают перебор.
5. **zapret не обходит блок по IP.** Если классификатор нашёл `IP_BLOCK` или
   `PORT_BLOCK` на **всех** IP цели, перебор стратегий **не запускается**.
   Пользователь сразу, первым шагом, видит: «Сайт заблокирован по IP-адресу.
   Подбирать стратегию бессмысленно, zapret такое не обходит. Нужен VPN или
   прокси». Рядом — доказательства (SYN без ответа, другие домены на этом IP
   тоже недоступны). Сразу же, автоматически, запускается **поиск другого,
   незаблокированного IP** этого ресурса (§2a). Если такой IP нашёлся,
   AutoTuner предлагает прописать его в hosts и подобрать стратегию уже для
   него. Если нет — итоговый вердикт «нужен VPN». Кнопка «Всё равно
   попробовать» на заблокированном IP есть только в режиме «Эксперт».
   Если заблокирована лишь часть IP домена, пользователь видит это, а перебор
   идёт только по живым IP.
6. **Каждый вывод подкреплён артефактом**: pcap, лог `--debug`, HAR,
   curl-trace. UI показывает, на чём основан вердикт.

## 1. Цели и что о них собирается

Вход пользователя: URL, домен, `IP:порт/протокол` или программа (§8).
Для каждого домена собирается:

- DNS: ответы системного резолвера, 2–3 публичных (UDP 53) и DoH. Сравниваем
  их, выявляем подмену и заглушки (`127.0.0.1`, IP заглушки провайдера,
  NXDOMAIN, отсутствие ответа);
- все A и AAAA, ASN и владелец сети (CDN: Cloudflare, Akamai, AWS, Hetzner,
  Fastly, Google) — нужно для §2.8 и группировки;
- поддерживаемые протоколы: HTTP/1.1, TLS 1.2, TLS 1.3, HTTP/3 (Alt-Svc / HTTPS RR),
  IPv6;
- ECH в HTTPS RR (DNS type 65), включён ли он у цели.

## 2. Классификатор блокировок

Тесты выполняются по порядку. Каждый тест даёт метку, у цели может быть
несколько меток.

| # | Метка | Как определить | Что делать |
|---|---|---|---|
| 2.1 | `DNS_POISON` | Системный DNS ≠ DoH, или IP из списка заглушек, или 302 на blocked-страницу по «системному» IP | Стратегия не поможет. Предложить DoH/DoT в ОС или браузере, экспорт «использовать DoH» для роутера. Дальнейшие тесты идут по IP из DoH |
| 2.2 | `IP_BLOCK` | TCP connect к IP:порт таймаутит (SYN без ответа), ICMP есть или нет, другой домен на том же IP тоже мёртв | **Стоп по этому IP.** Сразу сообщить «блок по IP, стратегия для этого адреса бессмысленна» (§0 п.5) и искать другой IP (§2a). Не нашёлся — «нужен VPN». Если другие IP домена живы, перебор только по ним |
| 2.3 | `PORT_BLOCK` | Ping отвечает, TCP 443 не соединяется, другие порты или UDP проходят | **Стоп**, как `IP_BLOCK` |
| 2.4 | `SNI_BLOCK` | Handshake TCP проходит, ClientHello с SNI цели → RST, таймаут или подмена. **Тот же IP с SNI нейтрального домена отвечает** (TLS alert или 409 — это нормально) | Основной случай для DPI-обхода |
| 2.5 | `PARTIAL_IP` | Нейтральный SNI на IP цели не проходит, а на своём IP проходит. Это IP-диапазонные правила | Обход «белым» SNI (`fake` с `sni=` из whitelist, `seqovl_pattern` с чужим CH) или не-TLS. Перебор с whitelist-фейками в приоритете |
| 2.6 | `HTTP_BLOCK` | HTTP 80: 302/307 на чужой SLD, RST или подмена ответа | `http_*`, fake+split на `http_req` |
| 2.7 | `QUIC_BLOCK` | HTTP/3: Initial уходит, ответов ≤ 1 (UDP-детектор 4/1) | `fake` QUIC или блок QUIC (браузер уйдёт на TCP). Рекомендуется проверить оба варианта |
| 2.8 | `CUTOFF_16K` | TLS проходит, загрузка «большого» ответа зависает на 14–24 KB входящих (pcap: входящие данные останавливаются, затем ретрансмиссии или RST). Проверка через GET большого ресурса или `CURL_PAD`-аналог (раздутые заголовки, чтобы набрать объём) | Обход whitelist-SNI (фейк и seqovl с SNI белого домена) или другой протокол. Тестируется только полной загрузкой |
| 2.9 | `PUNISH` | Сначала работает, через 1–3 попытки весь IP или сеть недоступны и без обхода, само проходит через N минут | Остановить перебор, выдержать паузу, снизить агрессию (repeats, частоту), отдавать предпочтение «тихим» стратегиям (seqovl без отдельных фейков) |
| 2.10 | `UNSTABLE` | Результат одной стратегии от попытки к попытке плавает (успехов 30–80%) | Балансировка DPI. Больше повторов, выбирать стратегию с 100% |
| 2.11 | `FINGERPRINT` | curl проходит, браузер нет (или наоборот) при одинаковом SNI. Отличаются наборы расширений, kyber, ALPN, размер CH | Подбирать на профиле реального клиента (§5) |
| 2.12 | `KYBER_MULTIPKT` | CH > MSS (X25519MLKEM768), DPI ловит только многопакетный CH, или стратегия не срабатывает (reasm) | Тест на профиле с kyber. Следить за `rawpacket_queue failed !`. Маркеры по reasm. На роутерах с fastpath — `--fastpath-workaround` |
| 2.13 | `ECH` | Блок по наличию ECH или по outer SNI (`cloudflare-ech.com`) | Тест с ECH и без. Совет отключить ECH в браузере, если обход ECH невозможен |
| 2.14 | `TLS13_BLOCK` | TLS 1.2 проходит, 1.3 нет | Отдельный перебор под 1.3 |
| 2.15 | `SECONDARY` | Основной домен открылся, страница сломана: падают поддомены или CDN (§4) | Перебор для каждого проблемного домена |

TLS 1.2 обходится труднее 1.3: в ServerHello сертификат виден открыто.
Если DPI режет по ответу сервера, это `wssize` (последнее средство) или
только 1.3.

Признаки DPI-ответа (против «честной» ошибки сервера):
- RST с TTL/IPID, не похожими на сервер (сравнить с SYN,ACK того же потока);
- RST приходит быстрее RTT сервера;
- HTTP 302/307 на чужой SLD, «blocked», «warning.rt.ru» и подобное;
- MITM-сертификат, издатель которого не совпадает с ожидаемым (CT log, pin);
- зависание после ClientHello (DPI дропает) при живом TCP.

## 2a. Обход блока по IP через другой адрес (hosts)

У CDN и крупных сервисов один домен обслуживается многими адресами, а
блокируют обычно не все. Если все IP, которые отдаёт DNS пользователя,
заблокированы, ищем другие.

**Откуда брать кандидатов:**
- ответы нескольких DoH-резолверов (Cloudflare, Google, Quad9, AdGuard,
  NextDNS) и публичных DNS из разных стран;
- EDNS Client Subnet с подсетями разных регионов (Google DoH поддерживает
  ECS): CDN отдаёт разные edge-адреса;
- `ipv4hint` / `ipv6hint` из HTTPS RR;
- IPv6-адреса домена (часто блокируют только IPv4);
- известные anycast-диапазоны провайдера CDN по ASN цели (Cloudflare,
  Fastly, Akamai, Google, AWS CloudFront). Это адреса, которые обслуживают
  любой домен этого CDN по SNI;
- адреса соседних доменов того же сервиса (например, `*.googlevideo.com`) и
  история успешных IP из базы знаний (§9).

**Проверка кандидата** (всё через встроенные пробы, без движка):
1. TCP connect на нужный порт — IP не заблокирован;
2. TLS с SNI цели: сертификат валиден **именно для домена цели** и цепочка
   доверенная. Без этого IP не принимается: иначе можно попасть на чужой
   сервер или MITM;
3. HTTP-ответ похож на настоящий (статус, ключевые заголовки сервиса,
   совпадение с эталоном, полученным через DoH и другой регион, если он
   доступен);
4. L2: большой ресурс грузится. Результат может оказаться `SNI_BLOCK` или
   `CUTOFF_16K` на новом IP — это нормально: дальше обычный подбор стратегии
   для этого IP.

Выбираем 1–3 лучших IP (стабильность, RTT, тот же регион, что у сервиса).

**Закрепление в hosts** (только с подтверждения пользователя, через Agent):
- файл: Windows `%SystemRoot%\System32\drivers\etc\hosts`, Linux
  `/etc/hosts`;
- записи в своём блоке `# BEGIN ZapretAutoTuner` … `# END ZapretAutoTuner`,
  остальное содержимое не трогаем. Перед записью делается резервная копия.
  После записи сбрасывается DNS-кэш (`ipconfig /flushdns`, `resolvectl
  flush-caches`);
- браузеры с DoH/«безопасным DNS» игнорируют hosts. Предупреждаем и
  предлагаем выключить DoH в браузере для этого сайта или в целом;
- в UI есть «Убрать записи AutoTuner из hosts» (одна кнопка).

**Дальше** подбор стратегии идёт на закреплённый IP как на обычную цель.
Финальная проверка L3 — с hosts в силе.

**Мониторинг (§9):** закреплённый IP проверяется регулярно. CDN меняет
адреса, и IP может умереть или начать отдавать чужой сертификат. Тогда
ищется новый кандидат, и hosts обновляется по той же политике «применять
сам / спрашивать».

**Экспорт:** закрепления идут отдельным разделом. Для ПК это блок hosts.
Для роутера — статическая DNS-запись: на Keenetic команда `ip host <домен>
<ip>` (CLI/веб), в dnsmasq `address=/<домен>/<ip>`. Если адресов несколько
или нужен IPv6, каждой паре домен–IP — своя строка. Без закрепления на
роутере стратегия для этого IP на других устройствах не сработает. Экспорт
предупреждает об этом явно.

## 3. Критерий «ресурс работает»

Тест-раннер выдаёт для каждой попытки структуру `ProbeResult`:
`{connect_ok, tls_ok, http_status, bytes_in, ttfb, duration, stalled_at, rst_seen, rst_origin_guess, alpn, tls_version, error}`.

Уровни проверки:

| Уровень | Чем | Условие успеха |
|---|---|---|
| L1 handshake | встроенный curl / наш TLS-клиент | TLS-handshake завершён, получен HTTP-ответ, сертификат валиден для домена |
| L2 body | GET крупного ресурса | Принято ≥ 64 KB **или** весь ресурс (по Content-Length), без stall > 3 с. Для `CUTOFF_16K` порог ≥ 128 KB |
| L3 page | headless-браузер (Playwright) | `load` наступил, все запросы к доменам цели завершились без net::ERR_*, нет stall. Снимаем HAR и скриншот |

- Поиск идёт на L1/L2 (дёшево). Финальная проверка — всегда L3 на
  каждом выбранном профиле клиента.
- Крупный ресурс для L2 ищется автоматически: из HAR берётся самый большой
  ответ домена (js/css/image). Если его нет, используется раздувание запроса
  заголовками до 20–32 KB (аналог `CURL_PAD`). Это вызывает блок 16 KB по
  объёму, даже если у сайта нет большой страницы.
- «Успех» при `http_status` 4xx/5xx допустим (сервер ответил). Неуспех —
  только сетевые признаки и DPI-ответы.

## 4. Вторичные домены

1. Открыть страницу в headless-браузере **через полноценный стек** (без
   прокси, с системным DNS или DoH по выбору), собрать HAR и сетевой лог CDP
   (Chromium) или webdriver-BiDi (Firefox).
2. Список доменов = все хосты запросов + `<link rel=preconnect|dns-prefetch>`
   + WebSocket + Alt-Svc. Дополнительно — SNI из pcap (ловит то, что
   браузер не отразил в HAR: QUIC, service worker).
3. Каждый домен помечается результатом (`ok`, `failed:<err>`, `stalled`,
   `blocked_by_client`). Блокированные рекламные/трекерные домены
   (EasyList) помечаются «не важно» и по умолчанию не чинятся.
4. Для каждого «важного» сломанного домена запускается классификатор (§2)
   и перебор (§6).
5. После исправления страница открывается заново. Итерации повторяются,
   пока не останется сломанных важных доменов (максимум 3 итерации: новые
   домены появляются, когда начинают грузиться скрипты).
6. Ограничения: домены из ответа, который не загрузился, не видны. Значит,
   цикл «починили → перезагрузили → нашли новые» обязателен.

## 4a. Режим «Хостинг-провайдеры» (без конкретного сайта)

Пользователь не вводит адрес, а отмечает провайдеров: Cloudflare, Akamai,
AWS (CloudFront и EC2), Google Cloud, Microsoft Azure, Fastly, Hetzner, OVH,
DigitalOcean, Linode, Vultr, Oracle Cloud, Scaleway, Contabo, Leaseweb,
G-Core и другие. Кнопка «Все крупные». Здесь обычно и срабатывает блок
«16 KB» по зарубежным хостерам (§2.8).

**Каталог провайдеров** — данные (`providers/*.json`), обновляются из UI:
- `asn[]`, источники диапазонов: официальные списки, где они есть (AWS
  `ip-ranges.json`, Google `cloud.json`/`goog.json`, Azure Service Tags,
  Cloudflare `ips-v4`/`ips-v6`, Fastly `public-ip-list`, Oracle
  `public_ip_ranges.json`, geofeed DigitalOcean и Linode), иначе анонсы ASN
  (RIPEstat announced-prefixes);
- `test_endpoints[]` — проверенные адреса с большим содержимым: speedtest и
  looking-glass провайдера (файлы ≥ 1 MB), публичные страницы на этом
  хостинге. У каждого — URL, ожидаемый SAN сертификата и размер;
- `sample_policy` — сколько IP из разных префиксов и регионов проверять.

**Как ищутся цели без адреса:**
1. Берутся `test_endpoints` провайдера.
2. Дополнительно проверяется выборка IP из диапазонов (по 2–5 из разных
   крупных префиксов и регионов, потому что правила DPI бывают
   «по диапазону», §2.5). Для каждого IP — TCP 443 и TLS без SNI или с SNI
   из PTR. Из сертификата (SAN) берётся настоящее имя хоста, и оно становится
   SNI теста. Хосты без валидного сертификата отбрасываются.
3. Если большого ресурса нет, используется раздувание запроса (аналог
   `CURL_PAD`), чтобы проверить блок по объёму.
4. Дальше обычный конвейер: классификатор (§2), перебор с доводкой
   (§6, §6.2a), критерий успеха L2 по объёму ≥ 128 KB.

**Успех для провайдера** — стратегия проходит на всех тестовых целях
провайдера (разные префиксы и регионы), 5/5. Если на части префиксов не
проходит, результат честно показывается как «работает на N из M
диапазонов», а проблемные диапазоны выносятся отдельно.

**Объединение** (§7) идёт по провайдерам так же, как по доменам: одна общая
стратегия или 2–3 группы.

**Экспорт:** профиль фильтруется не hostlist, а **ipset провайдера**
(`--ipset=…`). Это работает с первого пакета, hostname не нужен. Ipset
агрегируется (слияние соседних префиксов, как `ip2net`), чтобы списки AWS и
Azure не раздувались. Имена ipset в формате zapret-gui: `<provider>-ipset`
(например, `cloudflare-ipset`), см. `strategy-export` §5. В решении профиль
и ipset называются id провайдера (`cloudflare`), суффикс `-ipset` к имени
файла добавляет экспортёр.

**Как реализовано (фаза 6).** Каталог — `Core/Providers/Data/providers.json`
(форматы диапазонов: `text`, `geofeed`, `aws`, `google`, `fastly`, `oracle`,
`ripestat`, `azure`). `ProviderTargets.FindAsync`: тестовые эндпоинты плюс
выборка `CidrSet.Sample` (по адресу из разных префиксов, кандидатов вчетверо
больше нужного; смещение внутри сети — детерминированный FNV-хеш, одинаковый
между запусками), TLS без SNI → имена из SAN (`CandidateNames`: точные, затем
для `*.x.com` — `www.x.com` и `x.com`) → GET с этим SNI: валидный сертификат
и размер ответа. Цель с большим ответом (Content-Length или принято
≥ 128 KB, или обрыв после ≥ 8 KB) берётся первой, порог L2 128 KB; цель с
маленьким ответом — только если больших не хватило, с раздутым запросом
(32 KB) и требованием получить ответ целиком. Azure — Service Tags (ссылка на
файл с датой в имени ищется на странице загрузки, поле `link`), RIPEstat
AS8075 — только запасной источник с предупреждением (это вся сеть Microsoft);
у Hetzner — оба ASN (24940 и 213230). `ProviderTrialExecutor` гоняет
попытки по кругу по всем целям, попыток не меньше, чем целей: N/N значит
«на всех диапазонах». Списки диапазонов
устаревают: монитор (§9) периодически их обновляет и перепроверяет
стратегию.

## 4b. «Чекер» — быстрая сводка блокировок

Одна кнопка на главном экране. За 1–2 минуты показывает, что сейчас
заблокировано у пользователя, без подбора стратегий.

**Набор ресурсов** — данные (`checker/*.json`), обновляются из UI,
пользователь может добавить свои:
- сервисы: YouTube (сайт + `googlevideo.com` + QUIC), Facebook, Instagram,
  WhatsApp, X/Twitter, Discord (сайт + голос/UDP), Telegram (веб + MTProto),
  TikTok, LinkedIn, Spotify, ChatGPT, Netflix, Twitch, GitHub и другие;
- хостинг-провайдеры из каталога §4a (по 1–3 тестовые цели на каждого);
- контрольные «точно открытые» ресурсы (ya.ru и т.п.): если не открываются
  и они, проблема в сети, а не в блокировках.

**Что проверяется по каждому ресурсу** (параллельно, без движка, с
лимитом частоты): DNS (системный против DoH), TCP connect, TLS 1.3 с SNI,
загрузка ≥ 128 KB (блок 16 KB), HTTP/3, для UDP-сервисов — UDP-детектор.
Одна попытка на шаг и повтор только при неуспехе.

**Результат** — таблица-светофор с меткой классификатора (§2) простыми
словами: «Открывается», «Блок по SNI — обходится», «Обрыв на 16 KB —
обходится», «QUIC режется», «Подмена DNS», «Блок по IP — нужен VPN или
другой IP». Под таблицей — кнопка «Подобрать для отмеченных», которая
передаёт выбранные строки в мастер (сайты как цели, провайдеры в режим §4a).

**Повторный чекер при включённой стратегии** показывает колонки «без
обхода» и «с обходом», то есть сразу видно, что починено. История проверок
хранится, и можно сравнить «сегодня» и «неделю назад». Результаты чекера
пополняют базу знаний (§9).

## 5. Профили клиентов (браузеры и устройства)

Разные клиенты дают разный ClientHello: набор и порядок расширений,
наличие kyber, ALPN, GREASE, ECH, padding, размер, TLS 1.3-only, поддержку
QUIC. DPI и стратегии реагируют на это по-разному.

Профиль клиента = `{tls_fingerprint (JA3/JA4), kyber, ech, quic, ipv6, tcp_timestamps, mss, ttl_base}`.

Встроенные профили (минимум):
- Chrome/Edge latest (kyber, ECH, QUIC, GREASE);
- Firefox latest (kyber, ECH по DoH, QUIC);
- Safari/iOS (kyber X25519MLKEM768 только с iOS 26 и macOS 26, QUIC; ICMP-чувствителен);
- Android Chrome / WebView;
- Smart TV и старые клиенты (Tizen, webOS, Android TV 9–11, YouTube TV-app):
  TLS 1.2 и 1.3 без kyber, часто без QUIC, свой порядок расширений;
- curl (OpenSSL 3.5+ с kyber и без) — эталон blockcheck2.

Реализация:
- Реальные браузеры — Playwright с бандлимыми Chromium и Firefox. Это
  главный эталон для L3.
- Имитация отпечатков без браузера — библиотека-имперсонатор
  (curl-impersonate / собственный TLS-клиент на основе uTLS-подобных
  спецификаций CH). Позволяет на ПК проверить «как ведёт себя TV» без TV.
- Захват отпечатка реального устройства: пользователь открывает сайт на
  TV, ПК в той же сети ловит CH (если ПК — шлюз или точка доступа) или
  пользователь загружает pcap с роутера. Из CH строится новый профиль.
- TCP-параметры (`tcp_timestamps`, MSS, базовый TTL) влияют на fooling:
  `tcp_ts` бесполезен без timestamps (Windows), autottl зависит от базового
  TTL. Профиль хранит их.

Итог для пользователя: матрица «домен × профиль клиента». В экспорт идёт
стратегия, которая работает на всех отмеченных профилях (§7).

## 6. Перебор стратегий

### 6.1 Пространство (как blockcheck2, но управляемо)

Порядок от простых и «дешёвых» к сложным (номер — файл blockcheck2):

1. `10` http basic: `http_hostcase`, `http_domcase`, `http_methodeol`,
   `http_unixeol`.
2. `15` misc: `wssize` (только как последнее средство, помечается
   «режет скорость»).
3. `17` oob.
4. `20` multi: `multisplit` / `multidisorder` с pos ∈ {`1`, `2`, `method+2`,
   `midsld`, `1,midsld`, `sniext+1`, `host,endhost`, …}.
5. `23` seqovl: `multisplit:pos=…:seqovl=N:seqovl_pattern=…` (паттерны: нули,
   `0x1603030000`, блоб CH белого домена), `multidisorder` с seqovl-маркером.
6. `24` syndata.
7. `25` fake: `fake` с блобами {`fake_default_tls`, `0x00000000`, CH белого
   домена} × fooling × `tls_mod` {—, `rnd,dupsid`, `rnd,dupsid,sni=белый`,
   `padencap`} × repeats {1, 2, 6, 11}.
8. `30` faked: `fakedsplit` / `fakeddisorder` × pos × fooling × pattern.
9. `35` hostfake: `hostfakesplit` × host-шаблон × midhost × disorder_after.
10. `50/55/60` комбинации fake + multi / faked / hostfake.
11. `90` QUIC: `fake` с блобами `quic_initial_*` × repeats, `udplen`,
    ipfrag (IPv6).

fooling (blockcheck2 `FOOLINGS46_TCP`): `tcp_md5`, `badsum`,
`tcp_seq=-3000`, `tcp_seq=1000000`, `tcp_ack=-66000:tcp_ts_up`,
`tcp_ts=-1000`, `tcp_flags_unset=ACK`, `tcp_flags_set=SYN`. Плюс TTL
1..12, autottl delta 1..5 (`ip_autottl=-N,3-20`). Для IPv6 — `ip6_hopbyhop`,
`ip6_hopbyhop:ip6_hopbyhop2`, `ip6_destopt`, `ip6_routing`, `ip6_ah`.

### 6.2 Как перебирать быстро

- **Отсечение по классу** (§2): при `CUTOFF_16K` сначала whitelist-SNI
  варианты, при `HTTP_BLOCK` — http-функции, при `FINGERPRINT` — профиль
  клиента обязателен.
- **Отсечение по успеху** (как SCANLEVEL=standard): если `multisplit` сам
  работает, `fake+multisplit` не пробуем. Режим «Полный» = force.
- **Адаптивный поиск**: успешные стратегии по уже пройденным доменам того
  же провайдера и ASN проверяются первыми (локальная база знаний §9).
- **Параллелизм**: разные IP-цели можно тестировать параллельно, но
  каждому тесту нужен **свой** экземпляр движка с фильтром на IP цели
  (`--wf-raw-filter=ip.DstAddr==…` / nft set). Одну цель всегда тестирует
  один поток.
- **Ранний выход** для пользователя: «нашёл 3 рабочих, продолжить?»
- Каждая стратегия перед запуском проходит валидатор (nfqws2-engine §9).
- **Самообучение порядка** (PLAN 4a.1): многорукий бандит (Thompson
  sampling, Beta-апостериорные) ставит первым то, что срабатывало у этого
  пользователя на этом провайдере. Подробности — §6.2b.

### 6.2b Самообучение порядка перебора: как реализовано

- Код: `Core/Search/SearchLearning.cs` (`SearchLearning`, `ThompsonOrder`),
  данные — `KnowledgeBase.LearningHistory` (схема v3), подключение —
  `SearchOptions.Learning` (null = статический порядок). В приложении
  включено по умолчанию, выключается в настройках (`search.learning`).
- **Руки.** Уровень 1 — семейства из `families.yaml` и внешние источники
  (блок на источник: `prior` — сработавшее у провайдера, `llm` — советы
  модели). Уровень 2 — конкретные стратегии внутри блока (варианты
  параметров генератора и мутатора, ключ — канонический текст стратегии).
- **Счётчики** — из таблицы `trials` (успехи/попытки по дням), каждая
  попытка хранит `block_label` и `source` (`generator`, `mutation`, `prior`,
  `llm`). Вес результата падает вдвое каждые 30 дней.
- **Контекст и сжатие.** Вложенные уровни от широкого к узкому: всё →
  тип блокировки → ASN + тип → ASN + тип + профиль клиента (неизвестная
  часть пропускается). Каждый уровень стартует со среднего предыдущего с
  весом 4 псевдопопытки и добавляет свои счётчики: редкий контекст
  опирается на широкий, богатый говорит сам за себя. ASN провайдера вводит
  пользователь (офлайн, ничего не запрашивается); без него работают тип
  блокировки и общий уровень.
- **Порядок.** Руки без истории сохраняют порядок генератора (дешёвые
  первыми, по метке первыми). Одна выборка из априорного «неисследованного»
  делит известные руки на тех, кто идёт до неисследованных (по убыванию
  выборки), и тех, кто после. У внешних источников своё априорное
  (`prior` 0,7, `llm` 0,5), поэтому их результаты видны отдельно.
- **Гарантии.** Порядок — перестановка: ни одно семейство не выпадает,
  отсечения standard, пауза наказания, доводка, ранжирование и валидатор не
  меняются. Seed (`SearchLearning.Seed`) делает порядок воспроизводимым в
  тестах. Локальный поиск при ремонте (соседи текущей стратегии) идёт без
  бандита.

### 6.2a Доводка частично рабочих стратегий (обязательна)

Стратегия с КПД выше нуля, но ниже порога (например, 2/5) — это сигнал, что
направление верное. **Сначала доводим её и только потом переходим к
кардинально другой стратегии.**

1. **Порог.** «Частично рабочая» — от 1/N до (N-1)/N на этапе поиска.
   Сначала добираем попытки до 5–10, чтобы КПД не был случайным (2/5 и 2/10
   — разные случаи).
2. **Диагностика неудач.** По pcap и логу движка неудачной попытки
   определяем, где она сломалась:
   - фейк не дошёл до DPI или дошёл до сервера (TTL мал или велик, сервер
     ответил на фейк);
   - сработал DPI-RST или произошло зависание;
   - CH оказался многопакетным (reasm, kyber);
   - попытка ушла на другой IP или в другой балансировщик.

   От этого зависит, что менять в первую очередь.
3. **Мутации того же семейства** (не больше 1–2 параметров за шаг):
   - `repeats` 1 → 2 → 6 → 11;
   - другой fooling или комбинация двух (`tcp_md5` + `tcp_seq`, `badsum`);
   - TTL ±1–2 или переход на `ip_autottl` с другой delta;
   - соседние `pos` (`1`, `2`, `midsld`, `sniext+1`, `host`, `1,midsld`);
   - `seqovl` и паттерн;
   - другой блоб фейка (белый SNI, `0x00000000`, `fake_default_tls`);
   - `tls_mod` (`rnd,dupsid`, `sni=…`, `padencap`);
   - добавить второй фейк;
   - заменить `multisplit` на `multidisorder` или `fakedsplit`.
4. **Поиск.** Hill-climbing / beam (2–3 лучших ветки) с бюджетом попыток на
   доводку (по умолчанию 30 стратегий или 5 минут на цель). Мутация
   принимается, если КПД вырос с запасом (по доверительному интервалу
   Уилсона, а не по одной удачной попытке).
5. **Выход.** Достигли 5/5 (затем 10/10 на финальной проверке) — стратегия
   рабочая. Бюджет исчерпан без роста — лучший вариант запоминается как
   «частичный» с его КПД, и перебор продолжается со следующего семейства.
   Если ничего лучше не найдётся, частичная стратегия всё равно
   предлагается пользователю с честной пометкой «работает в ~X% случаев».
6. **Учёт.** История доводки (исходная стратегия → мутации → КПД)
   сохраняется в базе знаний (§9). В следующий раз у этого провайдера доводка
   начинается с лучшей найденной мутации.

То же правило действует в мониторинге (§9): деградировавшая стратегия
сначала доводится мутациями и только потом заменяется полным перебором.

### 6.3 Ранжирование рабочих

Score (меньше — лучше): число инстансов, отсутствие TTL-fooling (зависит
от маршрута), отсутствие `wssize` и `synack`, без своих блобов, работа без
`--in-range`, меньше `repeats`, стабильность 100%, работа на всех профилях
клиента, совместимость с целевыми платформами экспорта (keenetic: нет
Windows-only опций, zapret-gui: только штатные lua).

## 7. Объединение стратегий

Задача: множество доменов D, для каждого множество рабочих стратегий
S(d). Найти минимальный набор стратегий, покрывающий D (weighted set cover),
с предпочтением одной общей.

1. Нормализовать стратегии (канонический порядок аргументов, дедуп).
2. Если ∩ S(d) не пусто, взять лучшую по score стратегию из пересечения.
   Это одна общая стратегия для всех доменов (blockcheck2 COMMON).
3. Иначе — жадный set cover с весом score и `COVERAGE` (сколько доменов
   покрывает стратегия). Получается 2–4 профиля, каждый со своим hostlist.
4. **Перекрёстная проверка обязательна.** Стратегию-кандидата прогоняем на
   всех доменах группы, а не берём только из исторических результатов.
   Иначе пересечение неполно (blockcheck2 предупреждает: COMMON надёжен
   только при force).
5. Альтернатива для неразделимых доменов (один CDN, разные пути) —
   `circular` со стратегиями группы, лучшая первой (ротация начинается со
   `strategy=1`). `final` не ставим: ротация до `final` идёт, а на нём
   останавливается навсегда (zapret-auto.lua, `hrec.final~=hrec.nstrategy`),
   так что `final` на первой стратегии вообще отключает ротацию. Каждая
   стратегия после первой начинается со сброса фильтров
   (`--payload=all --in-range=x --out-range=a`, умолчания движка), иначе она
   наследует фильтры предыдущей. Помечается как «адаптивный» вариант.
6. Порядок профилей в экспорте: узкие hostlist-профили раньше общих.
   Hostlist совпадает и с поддоменами, поэтому профиль с `m.youtube.com`
   идёт раньше профиля с `youtube.com`, даже если доменов в нём больше.
   Если в hostlist-профиле есть техника фазы 0 (oob, syndata, wssize,
   synack), конфиг запускается с `--ipcache-hostname`, иначе она не
   сработает и Validator его не пропустит.
   QUIC-профиль отдельный. Профиль «все прочие» — по выбору пользователя
   (MODE_LIST / MODE_ALL / MODE_AUTO).
7. Финальная проверка объединённого конфига: **одним запуском движка со
   всеми профилями** L3 на всех доменах и профилях клиентов. Только это
   подтверждает, что профили не перехватывают друг друга.

## 8. Программы (не браузер)

Цель: пользователь выбирает установленную программу (exe или .desktop),
AutoTuner определяет, куда она соединяется, и подбирает стратегию.

- Windows: перечисление установленных (реестр Uninstall, Start Menu, UWP).
  Соединения по PID: `GetExtendedTcpTable` / `GetExtendedUdpTable`
  (опрос) + ETW `Microsoft-Windows-Kernel-Network` (события connect/send
  с PID, без пропусков коротких соединений) + DNS ETW
  (`Microsoft-Windows-DNS-Client`) для сопоставления IP→имя.
- Linux: `.desktop` и `$PATH`. Запуск в отдельной cgroup (`systemd-run
  --user --scope`) → `nft` с `socket cgroupv2` для точного перехвата.
  Соединения: `/proc/<pid>/net` + `ss -p`, опционально eBPF
  (`connect`/`sendmsg`).
- Записываем hostname: SNI/QUIC из pcap по 5-tuple, DNS-ответы, HTTP Host.
- Протоколы не-HTTP (игры, мессенджеры, VoIP): STUN, WireGuard, Discord,
  MTProto и `unknown` UDP. Оценка успеха — по детектору UDP (out ≥ 4,
  in ≤ 1 = неудача) и по стабильности потока.
- Сценарий: «Запустить и записать 60 с» → список хостов и портов → тот же
  конвейер §2–§7. Проверка — повторный запуск программы с включённой
  стратегией и сравнение метрик (байты in, длительность сессий, RST).

**Как реализовано (фаза 6).**
- Список программ: `ProgramCatalog.ListInstalledAsync` (Uninstall, `.lnk`
  в Start Menu через разбор MS-SHLLINK, UWP через `Get-StartApps`;
  `.desktop` и `$PATH` на Linux), дубли сливает `ProgramInfo.Merge` по
  **команде** (исполняемый файл + аргументы): все UWP идут через
  `explorer.exe shell:AppsFolder\…`, веб-приложения Chrome — через
  `chrome.exe --app-id=…`, Flatpak — через `flatpak run …`, и это разные
  программы. ANSI-строки `.lnk` — в системной кодовой странице (cp1251),
  RelativePath — от папки самого ярлыка, аргументы ярлыка разбираются по
  правилам Windows (`WindowsCommandLine`), обратные слэши не трогаются.
  `ProgramInfo.InstallDirectory` — папка программы (для UWP — папка
  пакета, для Uninstall — `InstallLocation`).
- Программа запускается из UI от имени пользователя, **не** Agent'ом.
  Agent только пишет захват (`StartCapture` без фильтра) и отдаёт сокеты
  по PID (`ListConnections`). Процессы программы — дерево запущенного PID
  плюс процессы из её папки (`InstallDirectory`, иначе папка exe; лаунчеры
  вроде `Update.exe` завершаются и оставляют детей; UWP запускает оболочка,
  и найти её процессы можно только по папке пакета); общая папка (`$PATH`,
  `C:\Windows`) не считается. Процессы отслеживаются по (PID, время старта)
  — переиспользованный PID чужой программы не попадает; пути exe читаются
  один раз на процесс (`ProcessImageCache`, `QueryFullProcessImageName`).
- Опрос сокетов раз в 500 мс: сокет короче этого не попадёт. ETW и
  cgroup — следующий шаг; сейчас точность — «потоки на локальных портах
  сокетов программы».
- `ProgramEndpoints.FromRecording`: потоки на этих портах, группировка по
  (L4, адрес, порт), без LAN, loopback, multicast и DNS. Имя — SNI, иначе
  из DNS-ответов в захвате. Протокол — `ProtocolDetector` по первому
  пакету **ровно как `protocol.c`/`desync.c`** (порядок тестеров тот же):
  QUIC Initial, Discord IP discovery (74 байта, тип 1, длина 70, 64 нулевых
  байта адреса), STUN (cookie, длина ≤ len−20 и кратна 4), DNS по
  заголовку, DTLS ClientHello/ServerHello (версии fe ff/fe fd/fe fc/01 00,
  длина записи помещается), WireGuard 148/92/64/32 байта (данные type 4
  ≥ 52 — только в уже известном WireGuard-потоке); TCP — TLS ClientHello,
  HTTP-запрос, MTProto только как obfuscated2: AES-256-CTR (ключ 8..40,
  IV 40..56) превращает байты 56..60 в `EF EF EF EF`. Сети Telegram и
  «голые» теги ef/eeeeeeee движок не признаёт — и мы тоже. UDP-поток
  ориентируется не по первому датаграмму: клиент — локальная сторона, иначе
  сторона без well-known порта, иначе эфемерный порт. Первые пакеты для
  повтора собираются после отсева ретрансмиссий, целиком (UDP — до 4
  датаграмм, TCP — до 64 KB; больше — поток помечается `truncated` и не
  повторяется).
  Здоровье — `FlowVerdict`, те же правила, что у монитора
  (`SessionClassifier.Outcome`, §9): UDP out ≥ 4 и in ≤ 1 → `NoReply`;
  RST от сети → `Reset`; обрыв на 8–32 KB с ретрансмиссиями → `Cutoff`;
  нет данных → `Stalled` только если поток старше 4 с к концу записи и
  клиент ретранслирует или это запрос-ответ (TLS/HTTP/MTProto) — молчащий
  сервер после ACK может быть long-poll. Поток младше 4 с к концу записи
  не оценивается. Один рабочий поток делает конечную точку рабочей.
- Подбор: TLS/QUIC/HTTP с именем — обычный конвейер по домену; остальное —
  по адресу. Генератор берёт протокол из `FromApp` (семейства `udp_fake`,
  `mtproto` и `tcp_generic` для нераспознанного TCP). Нераспознанный UDP и
  TCP — это пейлоад `unknown`: функции antidpi по умолчанию пропускают его
  (`payload=known`), поэтому каждому инстансу ставится `payload=unknown`, а
  стратегия ограничивается `--out-range=-d2`. Проба — `ReplayProbe`: повтор
  первых пакетов программы (для STUN — свежий binding request), успех —
  любой ответ (UDP) или данные без RST (TCP). Движок ограничен адресом и
  портом точки. Ошибки пробы — перечисление `ReplayError` с текстом RU/EN.
- **Повтор осмыслен не всегда** (`ReplayProbe.CanReplay`,
  `EndpointTrialExecutor.VerifyByRerunOnly`). Да: QUIC, публичный STUN,
  MTProto, DTLS не после ICE, TLS, неизвестный TCP/UDP. Нет: WireGuard
  (анти-повтор рукопожатия), Discord IP discovery (SSRC живой сессии), STUN
  с USERNAME/MESSAGE-INTEGRITY (проверка ICE), пустая или обрезанная запись.
  Для таких точек поиск повтором не запускается (`RunAsync` бросает
  `NotReplayableException` до старта движка, попытки не тратятся);
  стратегия проверяется только перезапуском программы (`ProgramCheck`).
- Проверка — `ProgramCheck`: один движок с профилем на каждую точку
  (по имени — hostlist, по адресу — `--ipset-ip`), программа запускается
  снова и записывается. Сначала процессы первой записи должны завершиться
  (иначе программа с одним экземпляром отдаст запуск старому, без
  стратегии): если они живы — ошибка «закройте программу / close the
  program», движок не стартует. Проходит, если хотя бы одна точка со
  стратегией теперь `Ok`, ни одна достигнутая не сломана (`Unknown` у
  слишком молодого потока — не сломана) и среди прочих нет сломанных.
- Экспорт: точки по адресу с одной стратегией и L4 — один ipset
  (`AddressResults.Program`), `--filter-l7` ставится, только если
  протокол распознан у всех точек группы.

## 9. Обратная связь с реальным трафиком (живой мониторинг)

Найденная стратегия проверяется не только синтетикой, но и в работе.

- Режим «Защита активна»: AutoTuner держит движок со стратегией и
  параллельно пассивно наблюдает трафик (ETW/pcap/conntrack) к доменам
  стратегии.
- Метрики на домен и стратегию за окно 5–15 мин: доля успешных TLS-сессий,
  ретрансмиссии на старте, RST от «не сервера», зависания на 16 KB, UDP
  out/in для QUIC, время до первого байта, средняя скорость.
- Сигналы из движка: `--debug=@file` в ограниченном объёме (ротация),
  срабатывания детектора `circular` и autohostlist (`--hostlist-auto-debug`).
- Деградация (доля неудач > порога 2 окна подряд) запускает **авто-доподбор**:
  1. перепроверка baseline (вдруг блок снят → предложить убрать домен);
  2. проверка текущей стратегии L2 из нескольких попыток;
  3. перебор «соседей» текущей стратегии (мутации: другой pos, fooling,
     repeats, блоб, sni) — локальный поиск, затем полный;
  4. горячая замена: новый профиль запускается вторым экземпляром на нужный
     домен, старый гасится после успеха (на Windows учитывать
     `--wf-dup-check`: фильтры у экземпляров должны различаться);
  5. запись в журнал и уведомление. Автоприменение — только с разрешения
     пользователя (настройка «применять сам / спрашивать»).
- Новые домены, которые появились в живом трафике и падают, предлагаются
  к добавлению (аналог autohostlist, но с подтверждением).
- Локальная база знаний: `{провайдер (ASN, внешний IP-диапазон), домен,
  ASN цели, класс блока, стратегия, профиль клиента, результат, время}`.
  Поиск стартует с того, что уже работало у этого провайдера. Экспорт и
  импорт базы — по желанию пользователя (никаких автоотправок).
