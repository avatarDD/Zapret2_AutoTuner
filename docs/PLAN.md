# Zapret2_AutoTuner — пошаговый план реализации

Кроссплатформенное (Windows и Linux) приложение на C#, которое на ПК
подбирает рабочие стратегии zapret2 (nfqws2/winws2) для заблокированных
ресурсов. Оно проверяет стратегии в реальных браузерах и на профилях
устройств, объединяет их в простой общий конфиг, экспортирует в zapret2,
nfqws2-keenetic и zapret-gui, а потом следит, как стратегия работает в
реальности, и подправляет её.

Справочники для разработки лежат в `.claude/skills/`:
- `nfqws2-engine` — ключи движка, WinDivert, профили, лимиты;
- `nfqws2-lua` — функции `--lua-desync`, аргументы, инварианты генератора;
- `dpi-diagnostics` — классификатор блокировок, критерии успеха, перебор,
  объединение, обратная связь;
- `strategy-export` — форматы zapret2, keenetic и zapret-gui.

Каждый шаг ниже заканчивается проверяемым результатом («Готово, когда»).
Шаги внутри фазы можно делать параллельно, если не указана зависимость.

## 1. Что решаем и для кого

Пользователь не знает, что такое fooling и seqovl. Он знает, что «не
открывается YouTube, Discord и сайт X, на телевизоре тоже». Ему нужно:
1. вписать сайты, IP с портом или выбрать программу;
2. нажать «Найти»;
3. получить понятный ответ («блокировка по SNI, обходится; блок по IP,
   zapret не поможет»), одну стратегию (или несколько) и кнопку «Экспорт»
   под свою систему: ПК, роутер Keenetic, zapret-gui;
4. знать, что стратегия продолжает работать, а если перестала, её подправят.

Подбор на ПК вместо роутера даёт:
- настоящие браузеры и полный HAR страницы;
- pcap и анализ;
- много попыток быстро;
- имитацию отпечатков других устройств.

## 2. Архитектура

```
┌────────────────────────── ZapretAutoTuner.App (Avalonia UI, без прав) ─────────────────────────┐
│ Мастер «Сайты → Диагностика → Подбор → Проверка → Экспорт», Монитор, Отчёты, Инструменты       │
└───────────────▲──────────────────────────────────────────────────────────────────────────────────┘
                │ gRPC поверх named pipe (Windows) / unix socket (Linux), аутентификация по токену
┌───────────────┴────────────── ZapretAutoTuner.Agent (привилегированный: admin / root) ──────────┐
│ EngineHost (winws2/nfqws2)  Firewall (nft)  Capture (WinDivert sniff / AF_PACKET)               │
│ ProcessTracker (ETW / eBPF+proc)  DnsProbe  Cleanup-гарантии                                    │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
ZapretAutoTuner.Core (общая библиотека, без ввода-вывода где возможно):
  Model (Target, ClientProfile, Strategy, Solution), Strategy.Catalog (функции и аргументы из skills),
  Strategy.Generator, Strategy.Validator, Strategy.Normalizer, Classifier, Unifier (set cover),
  Exporters (Zapret2, Keenetic, ZapretGui, Bundle), Importers, KnowledgeBase (SQLite)
ZapretAutoTuner.Probes:
  HttpProbe (свой HTTP/1.1 поверх TCP/TLS), HelloProbe (TLS-отпечатки), QuicProbe, DnsProbe, BrowserProbe (Playwright)
ZapretAutoTuner.Tools: менеджер бандла и загрузок инструментов, проверка хэшей и подписей
```

Решения и почему:
- **.NET 10 (LTS), C#.** Один код для Windows и Linux, self-contained
  publish, trimming.
- **Avalonia 11.** Нативный кроссплатформенный UI, тёмная и светлая тема,
  без WebView-зависимости. Альтернатива (MAUI) не поддерживает Linux.
- **Разделение UI и Agent.** Права нужны только для перехвата и захвата.
  UI не работает от root, а Agent маленький и проверяемый. На Windows
  Agent — служба или процесс через UAC «по требованию». На Linux — через
  `pkexec`/polkit, либо systemd-юнит. Agent гарантирует очистку правил
  firewall и остановку движка при падении UI (heartbeat).
- **Захват без Npcap.** На Windows захват делается через WinDivert в режиме
  `SNIFF` (тот же драйвер, что у winws2, отдельный handle с флагом sniff и
  фильтром на IP цели). На Linux — AF_PACKET (или NFLOG). pcapng пишем сами.
  Wireshark и tshark не обязательны: открыть pcap в Wireshark можно кнопкой,
  если он установлен.
- **Свой разбор пакетов** (TCP/UDP/TLS ClientHello/ServerHello/QUIC Initial
  с расшифровкой ключей Initial, HTTP). Нужен классификатору и JA4/JA3.
  Библиотеки: PacketDotNet для L2–L4, свой парсер TLS и QUIC (QUIC Initial
  расшифровывается по RFC 9001, ключи из DCID).

## 4. Пошаговый план

### Фаза 0. Каркас (неделя 1)

**0.1 Решение и сборка.** Solution, проекты из §2, CI GitHub Actions
(windows-latest, ubuntu-latest): build, test, publish self-contained
(win-x64, linux-x64, linux-arm64). EditorConfig, nullable, warnings as errors.
- Готово, когда: CI зелёный, артефакты публикуются.

**0.2 Модель и каталог.** `Strategy`, `Profile`, `Action`, `ClientProfile`,
`Target`. JSON-каталог функций и аргументов по skill `nfqws2-lua` и тест
сверки каталога с бандлимыми `lua/*.lua` (парсинг `-- arg :` и `^function`).
- Готово, когда: тест падает, если в lua пропала функция или аргумент.

**0.3 Бандл zapret2.** Скрипт `tools/bundle` скачивает закреплённый релиз,
проверяет SHA-256, раскладывает под `runtimes/<rid>/zapret2`. Проверка
`NFQWS2_COMPAT_VER_REQUIRED` против версии бинаря.
- Готово, когда: `winws2 --version` и `nfqws2 --version` запускаются из
  publish-папки.

### Фаза 1. Agent и движок (недели 2–3)

**1.1 Agent + IPC.** gRPC-контракт: `StartEngine(argv, scope)`,
`StopEngine`, `StartCapture(filter)`, `StopCapture → pcap`,
`Firewall.Apply/Remove`, `ListConnections(pid)`, `Heartbeat`. Запуск с
правами (UAC / pkexec), токен на сессию.
- Готово, когда: UI без прав запускает winws2 через Agent, а при убийстве UI
  Agent всё гасит за ≤ 5 с.

**1.2 EngineHost.** Сборка argv: `--lua-init` в правильном порядке,
`--blob`, профили. На Windows — `--wf-*` из портов и **ограничение на IP
цели** (`--wf-raw-filter=ip.DstAddr==… or ip.SrcAddr==…`), на Linux —
nft-таблица `inet ztuner` с set адресов цели, `queue num` из пула,
исключение `meta mark & 0x40000000`, sysctl `be_liberal`. Отдельная очередь и
экземпляр на каждый параллельный тест. Разбор stdout `--debug` в события
(выбор профиля, cutoff, `rawpacket_queue failed`, ошибки блобов).
- Готово, когда: интеграционный тест на Linux (network namespace) и Windows
  (runner с WinDivert) прогоняет `fake+multisplit` к тестовому серверу и
  видит модифицированные пакеты в pcap.

**1.3 Validator.** Правила `nfqws2-engine` §9 и `nfqws2-lua` §10: функции,
аргументы, блобы, payload-имена, размеры, `--dry-run`, `--intercept=0`.
- Готово, когда: каждая ошибка из списка покрыта юнит-тестом и даёт
  понятное сообщение на русском.

**1.4 Capture.** WinDivert sniff и AF_PACKET → pcapng, кольцевой буфер,
фильтр по 5-tuple или IP. Встроенный разбор TLS CH (SNI, JA4, kyber, ECH,
размер), QUIC Initial (расшифровка, SNI), RST-анализ (TTL/IPID против SYN,ACK).
- Готово, когда: на записанных образцах (корпус `tests/pcaps`) разбор
  совпадает с эталоном tshark.

### Фаза 2. Пробы и классификатор (недели 3–5)

**2.1 DnsProbe.** Системный DNS, публичные UDP 53, DoH (несколько
серверов), HTTPS RR (ECH, alpn), сравнение, метка `DNS_POISON`.

**2.2 HttpProbe.** Свой HTTP/1.1 клиент поверх TCP и `SslStream` вместо
бандла curl: в релизе остаются только официальные бинарники апстримов, а
нужные пробам детали (точка stall, RST, порядок байт) у своего клиента видны
лучше. L1/L2 на заданный IP, TLS 1.2 и 1.3,
GET крупного ресурса, раздувание заголовками (аналог `CURL_PAD`), замер
`bytes_in`, stall, ошибки. Результат — `ProbeResult` из `dpi-diagnostics` §3.

**2.3 HelloProbe и QuicProbe.** ClientHello профилей клиентов строится из
спецификаций (GREASE, порядок расширений, ML-KEM, ECH GREASE, padding), JA4
совпадает с настоящими браузерами. Проба отправляет его и смотрит ответ
сервера. QuicProbe шлёт свой QUIC Initial и читает Initial сервера.

**2.4 BrowserProbe.** Playwright: открыть URL в Chromium и Firefox, HAR,
сетевой лог, ошибки по доменам, `load`, скриншот. Режим «изолированный
профиль браузера» (без кэша и расширений, DoH на выбор). Браузер ищется так:
`ZT_CHROMIUM`/`ZT_FIREFOX`, каталог `browsers/` рядом с приложением, установка
Playwright. HAR, сохранённый пользователем в своём браузере, разбирается так
же (`Har.Parse`).

**2.5 Classifier.** Цепочка тестов из `dpi-diagnostics` §2 с
доказательствами. Без запуска движка: baseline, порт-тест, кросс-SNI тест
(нейтральный SNI на IP цели и наоборот), 16 KB тест, QUIC тест.
Порт-тест идёт первым после DNS. Если все IP цели заблокированы по IP или
порту, классификатор сразу выдаёт вердикт «блок по IP — для этого адреса
стратегия бессмысленна» и автоматически ищет другой, незаблокированный IP
ресурса (`dpi-diagnostics` §2a). Кандидаты берутся из DoH разных резолверов,
ECS разных регионов, HTTPS RR, IPv6 и anycast-адресов CDN. IP принимается,
только если сертификат валиден для домена. Если IP нашёлся, после
подтверждения пользователя он закрепляется в hosts (свой блок, бэкап, кнопка
отката), и подбор идёт на него. Если не нашёлся — вердикт «нужен VPN», цель
не попадает в перебор. Остальные цели продолжают проверяться.

**2.5a Закрепление IP.** Agent пишет блок `# BEGIN/END ZapretAutoTuner` в
hosts и сбрасывает DNS-кэш. Монитор (фаза 7) перепроверяет закреплённые IP.
Экспортёры выдают закрепления отдельно: блок hosts для ПК, `ip host` для
Keenetic, `address=/…/…` для dnsmasq.
- Готово, когда: на стенде, где у домена 3 IP и 2 заблокированы, AutoTuner
  находит третий, закрепляет его и подбирает стратегию. Запись в hosts
  убирается одной кнопкой.
- Готово, когда: на стенде с эмулятором DPI (§6) каждый тип блокировки
  определяется верно, а реальные отчёты пользователей воспроизводятся.

**2.5b Чекер.** Кнопка «Проверить блокировки» на главном экране
(`dpi-diagnostics` §4b). Набор ресурсов как данные: YouTube, Facebook,
Instagram, X/Twitter, Discord, Telegram и другие, плюс хостинг-провайдеры и
контрольные ресурсы. Параллельные быстрые пробы без движка, таблица-светофор
с причиной блокировки простыми словами. Оттуда одной кнопкой можно перейти к
подбору для отмеченных строк. С включённой стратегией видны колонки «без
обхода» и «с обходом». История проверок сохраняется в SQLite
(`Tuning/CheckerHistory`, фаза 3).
- Готово, когда: на стенде чекер за ≤ 2 минуты верно размечает все типы
  блоков по набору из 30 ресурсов.

**2.6 Вторичные домены.** HAR + pcap SNI → список доменов с важностью,
итеративное открытие (до 3 итераций). Состояния: ok, частично, ошибка,
stall, заблокирован браузером, только упомянут. Реклама и счётчики — список
как данные (`Diagnostics/Data/noise-domains.json`), по умолчанию не чинятся.
Самый большой ответ домена из HAR становится ресурсом для L2.

### Фаза 3. Генератор и перебор (недели 5–7)

**3.1 Generator.** Пространство blockcheck2 (`dpi-diagnostics` §6.1)
как данные, а не код: YAML-файлы «семейств» с параметрами. Порядок и
отсечения по классу блокировки. Режимы «Быстро», «Стандарт», «Полный».
- Сделано: `Core/Search/Data/families.yaml` (семейства, наборы значений,
  оси по режимам, отсечения по меткам), `StrategyGenerator`, белый
  ClientHello как блоб `tls_white`. Тест: ноль кандидатов, отвергнутых
  Validator, во всех режимах × протоколах × платформах.

**3.2 Runner.** Очередь испытаний: для каждой (цель × профиль клиента ×
стратегия) запустить экземпляр движка, пробу, собрать результат, повторить N
раз. Параллельно по разным целям, rate-limit на IP, детектор «наказания»
(`PUNISH`) с паузой. Прерывание и продолжение (состояние в SQLite).
- Сделано: `StrategySearch` (ядро перебора, без ввода-вывода) и
  `Tuning/AgentTrialExecutor`: один экземпляр движка через Agent на серию
  попыток, правило очереди только для адресов цели, L2-проба N раз, остановка
  движка в `finally`. Паузы между попытками и пауза при «наказании» (подряд
  `NoConnect`, затем проверка TCP без движка). Ход перебора (этап, %, прошло
  и осталось, найденные и лучшая частичная) — `SearchProgress`.
  Попытки, шаги доводки и чекпоинт пишет `KnowledgeBaseSearchLog`;
  `TuningSession.Prepare` при продолжении не повторяет уже испытанное, а
  стратегии, сработавшие у этого провайдера (ASN), ставит первыми.
  Параллельный перебор разных целей — несколько `StrategySearch` с разными
  `QueueNum`; запускать их будет UI (фаза 6).

**3.3 Доводка частично рабочих.** Если стратегия сработала, но КПД низкий
(например, 2/5), перебор не уходит к следующему семейству. Сначала:
1. добрать попытки, чтобы КПД был достоверным;
2. по pcap и логу неудачных попыток понять, где ломается;
3. мутировать ту же стратегию по 1–2 параметра за шаг (repeats, fooling,
   TTL/autottl, pos, seqovl, блоб, tls_mod, второй фейк) с hill-climbing и
   бюджетом попыток.

Если КПД не вырос, лучший вариант запоминается как частичный, и только тогда
начинается кардинально другая стратегия (`dpi-diagnostics` §6.2a).
- Готово, когда: на стенде с «балансировкой» DPI (одна из двух веток режет
  фейк по TTL) стратегия с исходным КПД 2/5 доводится до 5/5 мутацией, без
  перехода к другому семейству.
- Сделано: на стенде адрес `.21` — две ветки DPI по очереди на соединение
  (CONNMARK + statistic nth): одна сбрасывает `flaky.test`, другая
  `aky.test`. TTL-ветку на стенде не построить: между клиентом и сервером нет
  маршрутизатора, TTL не уменьшается. `multisplit:pos=midsld` проходит одну
  ветку (≈50%), доводка за один шаг находит `pos=midsld+1` (5/5) в том же
  семействе. Тест `StandSearchTests` с настоящим nfqws2 в CI.

**3.3a Ранжирование.** Score из `dpi-diagnostics` §6.3.
- Сделано: `StrategyScore` с разбором причин (ru/en) для UI.

**3.4 Финальная проверка.** L3 в обоих браузерах + отмеченные профили
устройств, 5/5, полная загрузка страницы и всех её важных доменов.
- Готово, когда: на стенде для каждого типа блока находится стратегия, а
  повторный запуск даёт тот же результат.
- Сделано: `Tuning/FinalCheck` — один экземпляр движка на стратегию, N/N L2,
  затем страница в браузере при работающем движке (L3 через
  `SecondaryDomains.PagePasses`). На стенде стратегия находится и
  подтверждается 5/5 для SNI-RST, SNI-drop и балансировки, повторный поиск
  даёт ту же стратегию. Блоки по IP и порту стратегией не лечатся (для них
  поиск другого IP, 2.5). Kyber и отпечаток на стенде ловят только
  браузерный ClientHello: их подбор проверяется L3 в браузере, на стенде
  это добавится вместе с UI (фаза 6). История чекера хранится в SQLite
  (`Tuning/CheckerHistory`).

### Фаза 4. Объединение (неделя 8)

**4.1 Unifier.** Нормализация, пересечение, weighted set cover,
перекрёстная перепроверка кандидатов на всех доменах группы, вариант с
`circular` (`dpi-diagnostics` §7).

**4.2 Проверка комбинированного конфига.** Один запуск движка со всеми
профилями, L3 по всем доменам и профилям клиентов.
- Готово, когда: для набора «YouTube + Discord + 3 сайта» выдаётся ≤ 2
  профилей TCP + 1 QUIC, и всё проходит L3.
- Сделано: `Core/Unify/Unifier` — нормализация (аргументы инстанса по имени,
  порядок инстансов сохраняется), пересечение, жадный weighted set cover (цена
  1 + score на новый домен), узкие профили раньше общих (поддомен раньше
  родителя), QUIC отдельно, вариант `circular` (`strategy=N` без пропусков,
  лучшая первой, без `final`, сброс фильтров между стратегиями,
  `--out-range=-s34228 --in-range=-s5556`), выгрузка в `Solution` с hostlist
  на профиль. `Tuning/UnifyRunner` — перекрёстная проверка лучших кандидатов
  на всех доменах группы со свежими результатами поверх истории (бюджет
  проверок делится между TCP и QUIC), `Tuning/ConfigCheck` — один запуск
  движка со всеми профилями (hostlist inline, `--ipcache-hostname` для
  техник фазы 0 в hostlist-профиле) и N/N L2 (+L3 через браузер) по каждому
  домену; QUIC-профили в запуске есть, но зондом не проверяются и
  возвращаются как непроверенные. На
  стенде: поиски дали `midsld` для двух доменов и `midsld+1` для третьего,
  перекрёстная проверка нашла одну общую `midsld+1`, общий конфиг прошёл
  одним запуском nfqws2; вариант `circular` проходит dry-run и lua-init
  движка. Набор «YouTube + Discord + 3 сайта» проверяется на реальной сети
  (unit-тест на этом наборе: 2 TCP + 1 QUIC).

мастера есть вкладка «Провайдеры» с галочками и кнопкой «Все крупные».
- Готово, когда: для Cloudflare, Hetzner и OVH находятся и проверяются на
  разных диапазонах стратегии против блока 16 KB, а экспорт с ipset

- Сделано: `Probes/Programs/ProgramCatalog` (Uninstall, `.lnk` Start Menu,

  программы), `Tuning/ProgramRecorder` (программа запускается от имени

  `Tuning/EndpointTrialExecutor` (повтор первых пакетов программы при
  движке, ограниченном адресом), `Tuning/ProgramCheck` (повторный запуск

### Фаза 7. Обратная связь и живой мониторинг (недели 11–12)

Требование: проверять, как стратегия работает в реальности, и на лету
вносить правки для её улучшения.

**7.1 Режим «Защита активна».** Agent держит движок с итоговой стратегией
на ПК (как обычный winws2 / nfqws2), а пассивный монитор считает метрики по
доменам стратегии (`dpi-diagnostics` §9): успешные TLS-сессии, ретрансмиссии,
DPI-RST, зависание на 16 KB, QUIC out/in, TTFB, скорость. Источники —
WinDivert sniff или AF_PACKET (только заголовки и CH, без содержимого),
`--debug` движка с ротацией, события детекторов `circular` и autohostlist.

**7.2 Детектор деградации.** Скользящие окна 5–15 мин, порог доли неудач,
гистерезис (2 окна подряд). Разделение «сайт лежит у всех» (проверка с
нейтральным SNI и без обхода, проверка по другим доменам того же CDN) и
«блок поменялся».

**7.3 Авто-доподбор.**
1. Перепроверка baseline: если блок снят, предложить убрать домен.
2. Локальный поиск вокруг текущей стратегии.
3. Полный перебор для домена.
4. Горячая замена без разрыва: новый экземпляр на домен с отличающимся
   фильтром, затем гасим старый.
5. Журнал «что поменялось и почему».

Политика применения — настройка пользователя: «применять сам» или
«спрашивать» (по умолчанию спрашивать). Экспортированные конфиги (роутер)
не трогаются: AutoTuner показывает «стратегия для роутера устарела, вот
новая» и предлагает повторный экспорт или доставку.

**7.4 Обратная связь с роутера.**
- Keenetic: по SSH (с согласия) читать `nfqws2.log` (autohostlist debug),
  `--debug` лог при `LOG_LEVEL=1`, `auto.list`.
- zapret-gui: эндпоинт статистики (п. 5.4) или MCP.
- Новые домены из auto.list и падающие домены подтягиваются в AutoTuner
  для доподбора.

**7.5 Пользовательский сигнал.** Кнопка «Не работает сейчас» в трее
(Windows) или индикаторе (Linux). Пользователь говорит, где сломалось
(сайт, программа, устройство), и AutoTuner сразу снимает pcap, HAR и запускает
доподбор. Это самый точный сигнал, его вес в базе знаний выше.
- Готово, когда: на стенде смена правил эмулятора DPI в течение работы
  обнаруживается ≤ 2 окон и чинится без участия пользователя (в режиме
  «применять сам»).

**7.6 Подбор и доводка прямо на zapret-gui (опционально).** AutoTuner
использует роутер с zapret-gui как место испытаний, а не только как цель
экспорта. Основа — уже готовые MCP-эксперименты zapret-gui
(`core/strategy_experiment.py`, инструменты `strategy_experiment_*` на
`POST /api/mcp`): они по очереди применяют варианты, меряют цели пробами
`tls`/`http`/`body` с самого роутера, отдают метрики, хвост лога движка и
подсказки, держат общий мьютекс движка и сами откатывают состояние по
дедмен-свитчу `ttl_sec` (снимок лежит на диске и переживает перезагрузку).
Свои временные стратегии `zt-trial-*` не нужны.
1. Подключение: адрес zapret-gui и MCP-токен вводит пользователь. AutoTuner
   просит только разрешения `experiments` (с ним `control` и `probes`) и
   чтение логов; консоль, файлы и запись настроек не нужны.
2. Пользователь один раз подтверждает «сессию испытаний на роутере»
   (правило 7). Всё, что меняет эксперимент, откатывается без `commit`;
   `commit` AutoTuner вызывает только по отдельному подтверждению
   пользователя (или сам, если включено «применять сам»).
3. `RouterTrialExecutor` реализует `ITrialExecutor`: кандидаты уходят
   пачками по 2–5 вариантов в один эксперимент (`variants[].profiles`:
   профиль кандидата первым, затем профили текущей стратегии, чтобы
   остальные сайты не теряли обход на время испытания), цели — домены
   подбора, пробы `body` (порог объёма как у L2), `repeats` = попытки.
   Метрики и подсказки эксперимента переводятся в `TrialOutcome`,
   лог движка идёт в отчёт. Победителя пачки AutoTuner оставляет
   (`keep_best`) и проверяет с ПК через роутер (L2/L3), прежде чем
   предлагать.
4. Поверх этого работает обычный перебор с доводкой (§6.2a): меняется
   только исполнитель. Так находится стратегия, которая работает именно на
   этом роутере (его ядро, offload, версия nfqws2).
5. После подбора zapret-gui остаётся источником обратной связи (7.4): логи,
   история экспериментов, autohostlist. Детектор деградации (7.2) решает,
   когда стратегия испортилась, авто-доподбор (7.3) повторяет испытания на
   роутере, журнал (7.3.5) пишет, что испытывалось и чем закончилось.
- Готово, когда: на стенде с zapret-gui смена правил DPI обнаруживается по
  обратной связи с роутера и чинится стратегией, испытанной на самом
  роутере, а при обрыве связи роутер сам возвращается к исходной стратегии.

### Фаза 8. UI и UX (сквозная, полировка на неделях 12–13)

Главный экран: большая кнопка **«Проверить блокировки»** (чекер, п. 2.5b) и
кнопка «Подобрать стратегию». Чекер — первое, что видит пользователь: сразу
понятно, что блокируется и как.

Главный сценарий — мастер из 5 шагов, всегда видно, что происходит и почему:

1. **Что не работает.** Поле «вставьте сайты, ссылки, IP:порт» (по одному
   на строку, понимает URL, `host:port/udp`, CIDR). Вкладка «Провайдеры»
   с галочками (Cloudflare, Hetzner, OVH, AWS… и «Все крупные»). Кнопки «Выбрать
   программу» и «Устройства» (чекбоксы: этот ПК — Chrome/Firefox, Android,
   iPhone, Smart TV, «другое» с захватом отпечатка). Готовые наборы
   («YouTube», «Discord», «Telegram», «Instagram»).
2. **Диагностика.** Для каждой цели карточка со светофором и простым
   объяснением: «Блокировка по имени сайта (SNI) — обходится». При блоке
   по IP карточка красная и показывается сразу, ещё до подбора: «Сайт
   заблокирован по IP. Для этого адреса искать стратегию бессмысленно. Ищу
   другой адрес…». Дальше одно из двух: «Нашёл рабочий адрес X. Прописать в
   hosts и подобрать стратегию?» или «Других адресов нет — нужен VPN или
   прокси». «Подробнее» показывает доказательства.
3. **Подбор.** Прогресс-бар по целям, «найдено рабочих: N», живая таблица,
   «Остановить и взять лучшее».
   Процесс поиска виден целиком (релиз 1):
   - общий прогресс: примерно сколько процентов пройдено и осталось,
     сколько времени прошло и примерно сколько осталось. Оценка считается
     по бюджету испытаний режима («Быстро», «Стандарт», «Полный») и средней
     длительности уже сделанных попыток, пересчитывается после каждой и
     помечается «≈». Ранний успех или отсечение семейств уменьшают остаток;
   - лента этапов для каждой цели: baseline → классификация → семейство
     стратегий N из M → доводка → финальная проверка, текущий этап выделен;
   - строка «сейчас»: какая стратегия испытывается, на каком профиле
     клиента, попытка k из n, что видит проба (handshake, байты, RST, тайм-аут);
   - промежуточные результаты по мере появления: частично рабочие с КПД,
     лучшая на данный момент, отброшенные семейства и почему;
   - журнал событий (раскрывается), из него же собирается «Собрать отчёт».
   Runner (3.2) публикует события `StageChanged`, `TrialStarted`,
   `TrialResult`, `CandidateFound`, `FamilySkipped`; UI только подписывается.
4. **Проверка.** Матрица «сайт × браузер/устройство» с галочками,
   скриншоты страниц, «полная загрузка: OK (2,3 MB)».
5. **Экспорт.** Плитки «Этот компьютер (Windows/Linux)», «Keenetic
   (nfqws2-keenetic)», «zapret-gui», «zapret2 на Linux-роутере», «Скопировать
   строку». У каждой — что получится и одна кнопка.

Прочее:
- «Монитор» (фаза 7): здоровье стратегий, график успехов, журнал правок.
- «Отчёты»: HTML-отчёт для обсуждения в чате или на форуме (без личных
  данных: IP пользователя маскируется).
- «Эксперт»: ручной редактор стратегии с подсветкой и автодополнением из
  каталога, валидатор на лету, «прогнать на цели».
- Локализация: русский (основной), английский.
- Доступность: клавиатура, крупный шрифт, тёмная тема.

### Отчёт для разбора неудачи (релиз 1)

Если рабочая стратегия не нашлась, кнопка **«Собрать отчёт»** упаковывает в
один архив (и в текст для вставки в чат) всё, по чему можно понять причину:
вердикт классификатора с доказательствами, таблицу попыток (стратегия,
уровень, успехов/всего, ошибка), выдержки `--debug` движка, сводку pcap
(RST, ретрансмиссии, где оборвалось), окружение (ОС, версия zapret2, VM,
антивирус, DoH). IP пользователя и, по выбору, домены маскируются. К
отчёту прилагается готовый промт для Claude: «вот отчёт AutoTuner, найди
причину и предложи правку стратегии». Ничего не отправляется само.

## 4b. Релиз 2 (после основного функционала)

1. **Локальное самообучение порядка перебора.** Алгоритм многорукого
   бандита (Thompson sampling по семействам и параметрам) запоминает, что
   срабатывало у этого пользователя на этом провайдере (ASN, внешний
   диапазон), и пробует это первым. Работает офлайн, без обучающих данных
   и серверов, хранится в локальной базе знаний.
2. **LLM-советник.** Собранный отчёт (п. «Отчёт для разбора неудачи»)
   отправляется языковой модели: Claude по API-ключу пользователя или
   локальная модель (Qwen/Llama через OpenAI-совместимый эндпоинт). В
   контекст кладутся наши skills по zapret2. Ответ — причина неудачи и
   предложенные правки, которые проходят Validator и проверяются обычным
   конвейером. Только по явной кнопке, ключ хранится локально.

3. **Обмен результатами между пользователями.** Пользователь по своей
   кнопке выгружает из локальной базы обезличенный пакет результатов и
   загружает чужие. Импорт служит априорным знанием для бандита (п. 1):
   что лучше работает на каком провайдере и для каких сайтов.
   - Пакет: JSON с версией схемы, подписан ключом установки (подделку
     видно, личность не раскрывается). Внутри: провайдер (ASN и название,
     без IP пользователя), регион по желанию, тип блокировки, цель (домен
     или категория), стратегия в синтаксисе nfqws2, профиль клиента, КПД
     (успехи/попытки), даты первой и последней проверки, версия zapret2.
   - Нет: IP, имён устройств, HAR, pcap, истории посещений, идентификаторов.
     Перед выгрузкой показывается всё, что уйдёт, можно вычеркнуть строки.
   - Импорт: каждая стратегия проходит Validator; чужой результат весит
     меньше своего и стареет со временем; дубли и противоречия сводятся
     по ASN и цели; одиночный источник не перебивает собственные данные.
   - Шаг 1 (без серверов): файл, которым делятся в чате или на форуме.
     Шаг 2: децентрализованный канал (общий GitHub-репозиторий с PR
     пакетов или p2p вроде torrent/IPFS), подписка по желанию.
   - Телеметрии по-прежнему нет: ничего не уходит без явного действия.
   Схема SQLite релиза 1 сразу хранит ASN, тип блокировки, профиль клиента
   и счётчики попыток, чтобы пакет собирался без миграций.

Своя обученная модель-ранжировщик с телеметрией не делается: нет данных, а
телеметрии в проекте нет.

| Риск | Мера |
|---|---|

## 6. Тестовый стенд (нужен с фазы 1)

- Сделано в фазе 2: `tools/stand/stand.sh` поднимает netns `ztstand`
  (veth, 10.124.0.x), «DPI» собран на правилах iptables (string, connbytes,
  u32, length), сервер — `tools/stand/server.py`. Интеграционный тест
  классификатора идёт в CI под root и проверяет, что netns убран.
- Дальше: Linux network namespaces: клиент ↔ «DPI» ↔ сервер. «DPI» — программа
  на nfqueue или eBPF, которая реализует типы блоков: SNI-RST, SNI-drop,
  16 KB cutoff (с whitelist SNI), QUIC-drop, HTTP-redirect, IP-drop,
  fingerprint (по JA4), «наказание», балансировка двух DPI с разными
  правилами. Сервер — nginx с TLS 1.2/1.3/HTTP3, большие файлы.
- На стенде проверяются классификатор, генератор, объединение, экспорт
  (запуск nfqws2 с экспортированным конфигом) и мониторинг (смена правил на
  лету).
- Windows: GitHub runner с WinDivert для интеграции EngineHost и Capture.

## 7. Мои предложения сверх запроса

1. **Agent отдельно от UI** — безопасность и надёжная очистка (§2).
2. **Захват через WinDivert sniff**, без Npcap: меньше установок и нет
   проблем с лицензией Npcap.
3. **Стенд с эмулятором DPI** — без него генератор и мониторинг не
   отладить, а реальный провайдер меняется.
4. **Локальная база знаний «провайдер → что работало».** Быстрый старт на
   новых доменах и после смены блокировок. Обмен — только файлом и по
   желанию.
5. **Импорт чужих стратегий** (из чатов, zapret-gui, keenetic) с ответом
   «работает ли у меня» — частый реальный сценарий.
6. **Кнопка «Не работает сейчас»** — самый ценный сигнал обратной связи.
7. **Отчёт для форума или чата** — пользователи и так делятся логами
   blockcheck, а тут будет понятный и обезличенный отчёт.
8. **Захват отпечатка устройства** (TV, приставка) для профиля клиента:
   решает «на ПК работает, на телевизоре нет».
9. **PR в zapret-gui с импортом бандла** — один файл вместо пяти ручных
   шагов.
10. **Подсказки по DNS** (DoH в браузере и ОС, DNS на роутере), потому что
    часть «не работает» — это DNS, и стратегия тут не поможет.
